## Observations

- Test ran against `http://localhost:4000` with 50 virtual users sustained for 60 seconds after a 10-second ramp.
- **`GET /api/animals` 500 errors** — all 253 error responses originated from this endpoint (15.67% error rate). The other three endpoints had zero errors. The most likely cause is Supabase connection pool exhaustion: the free-tier Supabase instance has a pooled connection limit (~25 connections), and `GET /api/animals` carries 50% of the scenario weight (≈ 25 concurrent VUs at peak). Under this pressure some Supabase queries fail and the server returns 500. Individual requests to the same endpoint succeed without error outside of peak concurrent load.
- **Latency was excellent for all endpoints** — overall p95 was 166ms and p99 was 400ms, well inside every SLO threshold. The server layer itself introduced no measurable overhead.
- The `GET /api/animals/filters` endpoint issues 4 parallel Supabase queries per request; despite this it maintained p95 207ms and zero errors, showing the connection pool handled fan-out well when not at full saturation.
- If running against a Vercel serverless deployment, cold-start overhead will inflate p99 compared to a persistent local server.
